## 1. 설계 원칙 (기존 계약 유지)

- **네이밍 위계 v7.9 A안 유지**: 섹션 산출물 = "미래 일기", 보드 층위 = "미래의 하루 이야기". 이번 개선은 이 위계를 *더 명확히 드러내는* 방향이지 이름을 새로 짓는 게 아니다.
- **Hick's law**: 완주 대시보드의 다음 행동은 "감상 1개 + 보조 1개"로 압축. 만들기 계열 UI는 완주 상태에서 치운다.
- **Peak-End**: 완주는 이 서비스의 피크. 첫 완주 순간의 연출(1회성)과 완주 상태의 상시 연출(재방문마다)을 구분해서 설계한다.
- **Endowment/IKEA**: 완주 화면의 주인공은 시스템 UI가 아니라 사용자가 만든 산출물(보드·한 문장·일기)이다.
- **높이 예산**: 대시보드 ≤1.2뷰포트(v71r3 R3-1b) 계약 유지 — 요소를 추가하면 반드시 다른 요소를 빼거나 접는다.

## 2. Slice 1 — 재방문자 로그인 진입 장치 (P1)

### 2-1. 흐름 진단

현재: 신규 기기 → 루트 → localStorage 빈 보드 → `/onboarding/1` → 2 → 3 → `/onboarding/choice`에서야 Google 버튼.
기존 회원은 자기 보드가 서버에 있는데도 온보딩 인터랙션(이름 입력·도토리 심기)을 강제로 다시 한다. 이름까지 새로 입력하게 되므로 "내 보드가 날아갔나?" 불안을 만든다.

로그인 인프라는 이미 전역이다: `AccountFlow`(레이아웃 상주)가 로그인 감지 → `/api/board` → `decideMerge` → 서버 보드 채택 시 `saveBoard(server)` + reload → 루트에서 `onboardingDone`으로 `/dashboard` 직행. **즉 온보딩 어느 지점에서 로그인해도 복원은 자동으로 작동한다. 필요한 건 트리거(링크)뿐.**

### 2-2. 설계

**온보딩 셸 하단에 상시 로그인 링크 1줄** (`OnboardingShell` — 3스텝 공통, ← 이전 버튼 위):

> 만들던 보드가 있어? **Google로 이어가기 →**

- 탭 → `signIn('google', { callbackUrl: '/' })`. 루트 리다이렉터가 복원된 보드 상태에 따라 배분한다(복원 성공 → /dashboard, 서버 보드 없음 → 진행하던 온보딩 스텝).
- 서버 보드가 없는 신규 사용자가 눌러도 흐름이 깨지지 않는다: 로그인 상태로 온보딩을 계속하고, choice 화면은 `authenticated`면 스킵되므로 온보딩 완료 시 바로 대시보드.
- 위치를 셸 하단으로 한 이유: 스텝 1(이름 입력)에서 가장 필요하지만, 스텝 2·3에서 "아 나 회원이었지"가 떠오를 수도 있다. 셸 공통 1줄이 구현도 가장 얇다.
- 카피는 "로그인"이라는 시스템 어휘 대신 **"이어가기"** — 서비스 전반의 반말 톤·"보드를 이어간다" 심상과 정합. (r2a 'Google로 로그인' exact 계약은 LoginNudgeSheet 쪽 버튼이므로 충돌 없음 — 신규 문자열로 추가만 한다.)

**choice 화면 카피 보강** (기존 회원이 게스트로 잘못 새기는 걸 방지):

> Google로 시작하기 버튼 아래 캡션 추가: "전에 만들던 보드가 있으면 그대로 이어져."

### 2-3. 엣지 케이스

- 로그인했지만 미등록(동의 전) → ConsentSheet가 전역에서 뜬다(기존 동작). 온보딩 위에 떠도 무방 — 동의 거절 시 signOut 후 게스트 온보딩 계속.
- 로컬에 이미 진행 중 보드(이름만 입력 등) + 서버 보드 존재 → `decideMerge`의 'ask' 분기(MergeSheet)가 기존 계약대로 처리. v8.1 merge 유실 가드 그대로.
- 스모크: 신규 기기 시뮬(스토리지 클리어) → 온보딩1에서 링크 노출 확인. 로그인 모킹 후 서버 보드 복원 → 대시보드 직행.

## 3. Slice 2 — 미래 일기 통합 열람 화면 `/diary` (P2 + 3안 검토)

### 3-1. 세 가지 안 비교

| 안 | 내용 | 평가 |
|---|------|------|
| ① 6편만 | 하루 이야기 폐기, 섹션 일기 6편만 | 사용자가 쓴 한 문장·통합 서사(피날레 산출물)를 버린다. 완주 보상이 약해짐. **탈락** |
| ② 통합 1편으로 재설계 | 6편을 아우르는 하루 일기 하나만 | 산출물이 1개로 깔끔하지만, 섹션별로 공들여 쓴 6편이 짜깁기 재료로 소모되고 다시 읽을 곳이 사라진다(IKEA 효과 역행). **탈락** |
| ③ 하루 일기 + 6편 모아보기 | 통합 하루 일기가 대표, 6편은 그 아래 원문으로 | 위계가 네이밍 A안과 정확히 일치: "미래의 하루 이야기"(보드 층위) ⊃ "미래 일기"(섹션 층위). 중복이 아니라 **본문과 부록** 관계로 재정의된다. **채택 권고** |

**③ 채택.** 단 화면을 합치는 것으로 끝내지 않고, ②의 문제의식(현재 통합 글이 '짜깁기'로 읽힌다)을 프롬프트 개선으로 흡수한다(3-4).

### 3-2. 새 라우트 `/diary` — 읽기 전용 열람 화면

현재 "다시 읽기"가 /finish(생성 플로우 페이지)로 가는 게 근본 문제다. /finish는 쓰기 플로우(pattern→sentence→story→complete)이고, 읽기 경험은 별도 화면이어야 한다.

구성(위→아래):

1. **헤더**: "📖 {이름}의 미래 일기" + 날짜 줄 "🗓️ {targetDate} — 그 삶이 이루어진 날"
2. **미래의 하루 이야기** (대표 글): futureDayStory 전문 + 사용자가 쓴 한 문장(blockquote, /finish complete 화면과 동일 처리)
3. **"이야기 다듬기" 보조 링크** → /finish story phase (다시 써줘 플로우 재사용 — 생성은 계속 /finish 소관)
4. **섹션 일기 6편**: DiarySheet의 목록 마크업 이관(섹션 색 보더 + renderStory). 기본 펼침, 섹션명 앵커.
5. 하단 보조 CTA: "내 비전보드 보기 →" (/collage)

- futureDayStory가 없는 부분 진행 사용자가 URL로 진입하면: 하루 이야기 자리에 "여섯 그루가 다 자라면 하루 이야기가 완성돼" 안내 + 있는 일기만 노출. (딥링크 가드 관례 — /finish의 onboardingDone 가드와 동일하게 적용)
6. DiarySheet 모달은 **폐기**하고 트리거를 /diary 링크로 교체 — 모달 1개 제거로 대시보드 코드도 얇아진다.

### 3-3. 대시보드 진입점 재편 (P2 해소)

- Before: "미래의 하루 일기 다시 읽기 →"(/finish) + "📖 미래 일기 6편 →"(모달) — 2개 병존.
- After: **"📖 미래 일기 읽기 →"(/diary) 1개.** 완주 시엔 주 CTA("완성한 내 비전보드 보기") 아래 보조 링크 자리, 완주 전엔 기존 DiarySheet 트리거 자리(📷 행 공유)를 그대로 승계.
- "미래의 하루 **일기**"라는 혼종 표기(v8.1에서 유입)는 전면 제거 — 보드 층위는 항상 "미래의 하루 이야기"로 표기 통일.

### 3-4. 프롬프트 개선 — '짜깁기'감 제거 (api/story)

현재 v8.0 프롬프트는 섹션 일기 6편을 재료로 넘기지만, 결과가 "섹션 순서대로 이어붙인 글"로 읽힌다는 게 오너 관찰. 개선 방향(계약: 반말 게이트 lib/honorific·30s 타임아웃 유지):

- **하루의 시간축으로 재구성 지시**: "여섯 영역을 순서대로 요약하지 말고, 아침→낮→저녁 하루의 동선 위에 자연스럽게 녹여라. 영역 이름(건강, 관계 등)을 소제목처럼 쓰지 마라."
- **분량·시점 고정**: 500~700자, 1인칭 현재형 "~다"체(기존 게이트), 마지막 문장은 사용자의 한 문장(oneSentence)을 변주해 닫기 — 피날레 느낌 강화.
- **중복 제거 지시**: 6편에서 겹치는 소재(같은 인물·장소)는 한 번만 등장시키기.
- 검증: `.claude/smoke-v80-story.mjs` 계약 스모크에 "영역명 소제목 미등장" 어서션 추가.

## 4. Slice 3 — 완주 대시보드 정리 (P3·P4)

`isFinished`(6/6 + futureDayStory) 상태에서 요소별 처리:

| 요소 | 현재 | 처리 |
|------|------|------|
| 완성한 내 비전보드 보기 | 주 CTA | **유지** (v8.1 계약 문자열 그대로) |
| 미래의 하루 일기 다시 읽기 | 보조 링크 → /finish | **"📖 미래 일기 읽기 →" → /diary**로 교체 (Slice 2) |
| 📷 질문 없이, 사진부터 담아볼래? | 상시 노출 | **완주 시 숨김** (`!isFinished` 조건 추가). 사진 교체·추가는 /collage 편집 모드가 담당 — 동선 중복 제거 |
| 📖 미래 일기 6편 (DiarySheet) | 모달 트리거 | **제거** (Slice 2로 흡수) |
| 진행 바 · 추천 카드 | isFinished면 이미 미노출 | 변경 없음 |
| 🗓️ 연도 라인 | "{연도}년의 나를 그리는 보드야 · 연도 바꾸기" | 완주 시 카피 전환: **"🗓️ {연도}년의 나를 그린 보드야"** (진행형→완료형) + **연도 바꾸기 링크 숨김**. 연도 편집은 /collage 편집(기존 동일 소스)에 남아 있으므로 기능 유실 없음 |
| walkCaption | "길 끝까지 다 걸었어 — 이제 네 보드를 즐기면 돼 🐿️" | 유지 (Slice 4의 연출과 세트) |

결과: 완주 대시보드는 "주 CTA 1 + 일기 링크 1 + 지도 + 완료형 캡션"으로 수렴. 만들기 계열 UI 전무 → '완성됐다'는 상태가 정보 구조 자체로 전달된다.

## 5. Slice 4 — 완주 연출 (P5)

### 5-1. 상시 연출 — 참나무가 다 자란 언덕 (WalkPathMap, allDone 시)

- **참나무 승격**: 도착점 🌳를 `text-title`(현재)에서 2배 스케일 + 완만한 글로우(완료 스테이션의 🌿 수풀 문법과 동일한 장식 레이어). 라벨 "참나무 언덕" → **"다 자란 참나무"**.
- **경로 전 구간 실선**: allDone이면 이미 buildSegments가 처리 — 변경 없음(확인만).
- **배경 그라디언트 완주 변주**: FOREST 그라디언트에 완주 전용 톤(예: 노을빛 하이라이트 1스탑 추가)을 `lib/colors.ts` FOREST 단일 소스에 `FOREST.gradientDoneCss`로 추가. DOM/canvas 락스텝 계약 준수 — 콜라주 숲 템플릿에는 적용하지 않음(대시보드 지도 전용).
- **참나무 언덕 탭 → /collage**: 코드에 "R3에서 딥링크 예정"으로 이미 예약된 항목. 완주 시에만 버튼화(aria-label "완성한 보드 보기"). 미완주 시엔 지금처럼 장식.
- 스테이션 아이콘·aria-label 계약(`${label} — ${STATUS_LABEL[status]}`)은 불변.

### 5-2. 1회성 연출 — 첫 완주 모먼트

- /finish "비전보드 완성 →" 확정(markBoardFinished) 후 **첫 대시보드 진입 1회**: 참나무 언덕에서 잎이 흩날리는 가벼운 파티클(CSS 애니메이션 6~8개 잎, 2초, `prefers-reduced-motion` 존중) + walkCaption 강조 페이드인.
- 스키마: `finishCelebrated` 플래그 1개 추가(스탬프형 — v7.8 storyWrittenAtCount와 같은 관례, 마이그레이션 불필요·없으면 미연출이 아니라 **연출 후 스탬프**).
- 토스트·모달은 쓰지 않는다 — 완주 직후 /finish complete 화면(폴라로이드 리빌)이 이미 피크 연출을 담당하므로, 대시보드는 "돌아올 때마다 완성돼 있는 풍경"이 컨셉.
