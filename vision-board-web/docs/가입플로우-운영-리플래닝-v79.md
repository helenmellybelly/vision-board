## 2. 회원·이용 현황 관리 (질문 1 답변)

### 2-1. 가입 유저 정보는 어디서 보나
| 방법 | 내용 | 상태 |
|---|---|---|
| **`/admin` 페이지 (신규)** | 프로덕션에서 **helen 계정으로 로그인 후** `vision-board-web.vercel.app/admin` 접속. 가입자 수·7/30일 추이·마케팅 동의자(동의 시각 포함)·보드 최근 저장 시각을 한 화면에서 확인. 다른 계정·비로그인은 404. | ✅ 이번 세션 구축 |
| Neon 콘솔 | console.neon.tech → 프로젝트 → SQL Editor. 아래 쿼리 복붙. | 기존 |

자주 쓸 SQL (Neon 콘솔용):
```sql
-- 전체 가입자 + 마케팅 동의 여부
SELECT email, name, marketing_consent, marketing_consent_at, created_at
FROM users ORDER BY created_at DESC;

-- 마케팅 동의자만 (뉴스레터 발송 대상)
SELECT email, name, marketing_consent_at FROM users WHERE marketing_consent;

-- 최근 7일 활동 유저
SELECT u.email, b.updated_at FROM boards b JOIN users u ON u.id = b.user_id
WHERE b.updated_at >= now() - interval '7 days' ORDER BY b.updated_at DESC;
```

### 2-2. 유저는 언제·어떻게 마케팅 동의를 하고 가입하나 (현행 플로우)
```
방문 → 온보딩 3스텝 → 선택 화면(Google로 시작 / 게스트로 시작)
  ├─ 게스트로 시작 → 사진 1장 담은 뒤 첫 대시보드 방문 때 소프트 게이트 1회
  │                  ("Google로 로그인해두기" / "나중에 할게") → 닫으면 7일 간격 배너 재유도
  └─ Google 로그인(OAuth) → 이 시점엔 아직 "가입" 아님(DB에 아무것도 안 씀)
        → 동의 시트: [필수] 개인정보 수집·이용(이메일·이름만) + [선택] 마케팅 정보 수신(기본 해제)
        → [시작하기] 클릭 = 이 순간이 가입 (users 행 생성, 동의 여부·시각 함께 기록)
```
- 마케팅 동의는 **가입 순간 선택 체크박스**로 받고, `marketing_consent_at`에 동의 시각이 저장됨(법적 증빙 가능). 마이페이지 시트에서 언제든 철회 가능(철회 시각도 갱신). 미체크로도 가입 가능(정보통신망법 분리 동의 원칙 준수). → **"마케팅 동의 절차가 포함되어 있는가"에 대한 답: 예, 완전 구현되어 있음.**

## 3. 가입 시점 분석 & 리뷰 (질문 3 답변)

### 3-1. "사진을 등록하는 순간 데이터 저장"의 실제 동작
사용자 추정과 실제가 다릅니다:
- **게스트**: 사진 등록 시 **이 기기의 브라우저(localStorage)에만** 저장. 서버 전송 0. → 기기 변경·브라우저 데이터 삭제 시 유실.
- **로그인(가입) 유저**: 저장할 때마다 2.5초 디바운스 후 서버로 미러링(사진은 base64→Blob URL 승격 후 보드 전체 upsert).
- 즉 "사진 등록 = 저장"이 아니라 **"가입 = 서버 저장 시작"**이며, 사진 등록은 가입 유도(소프트 게이트)의 **트리거**로 쓰이고 있음.

### 3-2. 현 가입 시점이 최적인가 — 평가: **적절함 (유지 추천)**
행동설계 관점 근거:
- **보유 효과(Endowment) + 손실 회피(Loss Aversion)**: 첫 사진을 담아 "내 것"이 생긴 직후가 '잃지 않으려고' 로그인할 동기가 최대인 순간. 현 소프트 게이트가 정확히 이 지점(첫 사진 → 첫 대시보드 방문)에 위치.
- **IKEA 효과**: 채팅으로 답을 만들고 사진을 고른 투자가 쌓일수록 보드의 주관적 가치가 커져, 뒤로 갈수록 전환 확률이 오히려 상승. 선(先)가입 강제보다 유리.
- **BJ Fogg(동기×능력×프롬프트)**: 게이트 시점엔 동기(잃기 싫음)와 프롬프트(시트)가 갖춰졌고, Google 원탭이라 능력 장벽도 낮음.

대안 비교:
| 방식 | 장점 | 단점 | 판단 |
|---|---|---|---|
| 온보딩 선가입 강제 | 유저 데이터 100% 확보 | 가치 경험 전 이탈 급증(회원가입 벽), "가입은 관문이 아니라 잃지 않기 위한 선택" 원칙 붕괴 | ❌ |
| **현행: 첫 사진 후 소프트 게이트** | 가치 경험 후 유도 → 전환 질 높음, 이탈 최소 | 게이트 전 이탈 유저는 추적 불가(게스트) | ✅ 유지 |
| 게이트 시점 앞당김(첫 일기 직후) | 첫 감동 순간 활용(피크) | 몰입 흐름(일기→사진)을 끊음 | 데이터 보고 판단(§5 GA 퍼널로 게이트 도달률·수락률 측정 후) |

**단, 보완 제안 2건** (§4 백로그 P-2·P-3): 게이트를 닫은 게스트에게 "유실 리스크"를 더 구체적으로 알리는 카피, 로그아웃 직후 랜딩 경험.

## 4. 유저 플로우 개선 백로그 (제안 — 우선순위·규모 포함)

각 항목 = 문제 → 제안 → 근거 → 규모. **결정 필요** 표시가 있는 것만 오너 선택이 필요합니다.

### P-1. 계정 진입점을 대시보드 밖으로 확산 — **결정 필요**
- 문제: 콜라주·완성·씬 화면에서 계정/로그아웃 접근 불가. "로그아웃 버튼이 안 보인다"의 구조적 원인.
- 제안 옵션: **(a) 콜라주+finish 헤더에 AccountButton 추가**(추천 — 체류가 긴 두 화면만), (b) 공용 헤더 컴포넌트로 전 페이지 통일(규모 큼), (c) 현상 유지.
- 규모: (a) 소(파일 2개), (b) 중.

### P-2. 게스트 유실 리스크 고지 강화 — **결정 필요**
- 문제: 배너 카피 "보드가 아직 이 기기에만 있어"는 상태 서술이라 손실이 추상적.
- 제안: 손실을 구체화한 카피로 A/B — 예: "브라우저를 정리하면 이 보드는 사라져 — 1번의 로그인으로 지켜둘 수 있어". (손실 회피 프레이밍, 과장 없이 사실만)
- 규모: 소(카피 1줄). GA 도입 후 배너 클릭률로 검증.

### P-3. 로그아웃 후 랜딩 경험
- 문제: 이번 수정으로 홈('/')에 내리지만, 홈은 신규 온보딩 중심이라 "방금 로그아웃한 사람"에게 어색할 수 있음.
- 제안: 1차는 현행 유지(홈에서 보드 존재 시 대시보드 재진입 동선이 이미 있음). 재로그인 유도 토스트는 과설계로 보류.
- 규모: 0 (관찰 후 판단).

### P-4. 마케팅 동의 수락률 개선 — **결정 필요**
- 문제: 선택 동의 문구가 "정보를 받아보는 것에 동의합니다"로 가치 제안 없음 → 수락률 낮을 것.
- 제안: 받는 것이 무엇인지 구체화 — 예: "보드를 이어갈 힌트와 새 기능 소식을 가끔 보낼게 (월 1–2회, 언제든 해제)". 빈도 명시가 신뢰를 만들고 수락률을 올림(구체성 원칙).
- 규모: 소(카피 1줄). `/admin`의 동의율 지표로 전후 비교 가능.

### P-5. '미래의 하루' 네이밍 위계 정리 — §6 참고, **결정 필요**

### P-6. 다음 행동 안내 일관성
- 문제: 대시보드 CTA가 상태에 따라 최대 3종(추천 카드+마일스톤+콜라주)이라, 중복 제거 후에도 "다음 하나"가 흐려질 수 있음.
- 제안: "화면당 다크 CTA는 1개" 원칙을 컴포넌트 주석·검증 스위트에 계약으로 명문화(이번에 스위트에 단언 추가함). 추가 개편은 보류(Hick's law 관점에선 이미 추천 카드가 '다음 하나'를 담당).
- 규모: 0 (계약화 완료).

## 5. 데이터 분석 설계 (질문 2 답변)

### 5-1. 이번 세션에 구축된 것
- **GA4 연동 코드**: 측정 ID(`NEXT_PUBLIC_GA_ID`)가 등록되면 자동 활성. 미등록 상태에선 아무것도 로드하지 않음(성능·프라이버시 영향 0).
- **이중 전송 래퍼**(`lib/analytics.ts`): 기존에 심어둔 track() 이벤트 10여 종이 Vercel Analytics와 GA4로 **동시에** 전송됨. Vercel 무료 플랜에서 커스텀 이벤트가 무시되는 한계를 GA4(무료·무제한)가 메꿈. 이벤트에 보드 본문은 절대 미포함(기획서 §7 원칙 유지).

### 5-2. helen님이 하실 것 (2가지, 총 ~10분)
1. **GA4 속성 만들기**: analytics.google.com → 관리(⚙) → 속성 만들기 → 플랫폼 "웹" → URL `vision-board-web.vercel.app` → 생성된 **측정 ID(G-로 시작)** 를 저에게 전달 → env 등록·재배포는 제가 처리.
2. **Vercel Web Analytics 켜기**: vercel.com 대시보드 → vision-board-web 프로젝트 → Analytics 탭 → Enable. (코드는 이미 들어가 있어 버튼만 누르면 페이지뷰 수집 시작)

### 5-3. 핵심 퍼널 정의 (GA4에서 볼 것)
```
방문 → 온보딩 완료 → 첫 섹션 대화 시작 → 첫 일기 생성 → 첫 사진
  → 소프트 게이트 노출(login_nudge_shown) → 로그인 클릭(login_nudge_click)
  → 가입 완료(signup_consent_done, marketing 여부 포함) → 첫 보드(3섹션) → 완성(6섹션)
```
기존 이벤트 매핑: `login_nudge_shown/click`(게이트·배너·배경화면 출처 구분), `signup_consent_done{marketing}`, `login_merge_choice`, `photo_first_entry`, `collage_view`, `wallpaper_save`, `curated_category`, `scenes_more_open`.
**빈 구간**: 온보딩 완료·첫 대화·첫 일기 이벤트가 없음 → GA4 데이터가 쌓이기 시작하면 이 3개를 추가하는 게 다음 슬라이스 후보(각 1줄).

## 6. '하루 그리기' 노출 시점 의견 (요청 2 답변)

### 진단: 걱정하신 문제는 이미 구조적으로 해소되어 있고, 남은 건 '보이는 방식'
- **섹션별 미래 일기는 이미 존재**: 각 섹션 대화가 끝나면 **사진을 담기도 전에** 그 섹션의 "미래의 하루" 일기가 즉시 생성·표시됨. 첫 결과물은 첫 섹션에서 바로 나옴.
- **전체 이야기도 완주를 요구하지 않음**: 3/6 섹션 완료면 "첫 보드"로 조기 개방(v7.8), 6/6은 상향 목표.
- 그런데도 "다 완료해야 보여준다"로 느껴진 이유: ① 섹션 일기와 전체 이야기가 **같은 '미래의 하루' 이름**을 쓰고, ② 대시보드에서 이미 쓴 섹션 일기를 **다시 읽을 진입점이 없어** 결과물이 쌓이는 감각이 없으며, ③ CTA 중복(수정됨)이 위계를 흐림.

### 제안 옵션 — **결정 필요**
| 옵션 | 내용 | 효과 | 규모 |
|---|---|---|---|
| **A (추천)** | 네이밍 분리: 섹션 층위 = "**미래 일기**", 보드 층위 = "**미래의 하루 이야기**" + 대시보드 스테이션에서 쓴 일기 **다시 읽기** 진입 추가 | 결과물이 6개씩 쌓이는 감각(수집·진행 동기, goal-gradient) + 개념 혼동 제거 | 중(카피 여러 곳+진입점 1개) |
| B | A + 첫 일기 생성 직후 마이크로 보상(일기 카드 저장/공유 1버튼) | 피크 순간을 공유 루프로 연결 | 중 |
| C | 현상 유지(이번 CTA 중복 제거만) + GA 퍼널로 첫 일기 도달률 관찰 후 결정 | 데이터 기반 판단 | 0 |

> 의견: **섹션마다 간단한 미래 일기를 보여주는 방식이 낫냐는 질문에는 "이미 그렇게 되어 있다"가 답**이고, 투자할 곳은 생성 시점이 아니라 **재열람·네이밍·수집감**입니다. A만으로 충분하고, B는 A의 데이터가 좋을 때.
